# Участие в проекте

> Issues and pull requests in English are welcome — the project documentation
> itself is written in Russian.

Спасибо за интерес к Chronica. Ниже — минимум того, что нужно знать, чтобы
пул-реквест приняли без долгих кругов.

## Прежде чем писать код

- Прочитайте [`docs/BUILD.md`](docs/BUILD.md) — как собрать и что гоняет CI.
- Крупные изменения стоит сначала обсудить в issue: у ядра есть публичные
  контракты, против которых уже написаны macOS- и Android-оболочки.
- [`docs/STATUS.md`](docs/STATUS.md) — инженерный журнал по раундам. Там видно,
  почему что-то сделано именно так, и что уже пробовали.

## Ветки и PR

- Ветвитесь от `main`; имя ветки — `feature/<коротко>` или `fix/<коротко>`.
- Один PR — одна тема. Рефакторинг «заодно» лучше отдельным PR.
- В описании: что меняется, зачем, и как вы это проверили. Если поведение
  видимо пользователю — приложите пункт для `CHANGELOG.md` в раздел
  `[Unreleased]`.
- Публичные контракты ядра (сигнатуры, FFI-типы, форма событий) расширяются
  **аддитивно**: новые поля и методы — да, переименования и смена типов — только
  с явным обсуждением. То же правило действует для HTTP API v1
  (см. [`docs/API.md`](docs/API.md)) и для схемы БД: изменения приезжают
  миграцией, а не переписыванием.

## Гейты качества

PR должен проходить ровно то же, что и CI:

```bash
cd core
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo check --features ffi

cd ../apple
swift build
swift test
```

Уровни линтов зафиксированы в `[lints]` в `core/Cargo.toml` — понижать их в PR
не надо.

## Тесты — на поведение, а не на реализацию

Это главное требование к тестам в проекте.

- Проверяйте наблюдаемый результат и контракт, а не приватные поля, точные
  строки логов или порядок вызовов. Тест не должен краснеть от honest-рефакторинга.
- Тестам, которым нужны веса модели, устройство или нативная библиотека, ставьте
  `#[ignore]` (Rust) или `@Ignore` (Kotlin) с пояснением, почему.
- Регрессия на баг — это тест, который падал бы до фикса. Приложите его.

## Язык и стиль документации

- Doc-комментарии (`//!`, `///`, KDoc) и файлы в `docs/` — **на русском**.
- `README.md` — на английском, `README.ru.md` — русский эквивалент. Меняете
  один — синхронизируйте второй.
- Интерфейс локализован (en, ru) через String Catalog; как добавить строку —
  [`docs/BUILD.md`](docs/BUILD.md) §5.
- Комментарий объясняет **почему**, а не пересказывает код.

## Чего не коммитить

- **Сгенерированные UniFFI-биндинги руками.** Они пересоздаются
  `apple/Scripts/build-core.sh` (Swift) и `android/build-core.sh` (Kotlin) при
  каждой сборке; ручная правка молча потеряется.
- Артефакты сборки: `core/target/`, `apple/.build/`, `apple/dist/`,
  `apple/lib/` — всё в `.gitignore`.
- Веса моделей, записи, файлы `*.sqlite`, персональные данные и любые
  фрагменты реальных расшифровок.
- Секреты подписи, `.p12`, пароли, токены.

## Уязвимости

Не через issue и не через PR — см. [`SECURITY.md`](SECURITY.md).
