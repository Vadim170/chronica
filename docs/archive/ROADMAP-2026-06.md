> Аудит показал: инженерное ядро зрелое (обработка ошибок, поведенческие тесты, кроссплатформенность,
> crash-диагностика). Пробелы — в инфраструктуре и точечном техдолге. План ниже НЕ добавляет фич —
> только доводит существующее до продакшн-уровня.

## Фаза A — Надёжность кода (техдолг из аудита)

1. **`model_manager.rs` — устойчивая загрузка моделей.** Сейчас единичный `ureq::get().call()`:
   обрыв сети = ошибка с нуля. Нужно: retry с экспоненциальным бэкофом (3–5 попыток),
   докачка через HTTP `Range` (файл `.part` уже есть — возобновлять, а не перезаписывать),
   честная проверка sha256 там, где дайджест известен (сейчас реестр весь с пустыми sha256 —
   проверка мёртвая).
2. **`Engine.swift` — не глотать ошибки.** `download()` через `try?` теряет сбой загрузки модели
   (пользователь видит лишь зависший прогресс) → surface в `lastError`. Аналогично ревизия
   остальных `try?` (store-запросы → пустой результат маскирует проблемы БД — как минимум логировать).
3. **Пайплайн — видимость сбоев ASR.** Ошибка транскрипции чанка сейчас молча пропускается;
   добавить счётчик ошибок в метрики + событие при серии сбоев. Rust-паника в `tc-asr` оставляет
   транскрипцию стоящей до рестарта — защитный `catch_unwind` на интервал + событие Error.
4. **Рассинхрон документации.** STATUS.md описывает Android как mock/stub — код опережает
   (реальный sherpa в jniLibs, SystemAudioCapture реализован). Синхронизировать.

## Приоритет 1 — Mac UI: упростить меню-бар, одно современное окно

**Проблема:** клик по иконке открывает крупный popover, перекрывающий соседние иконки;
функции размазаны по popover + двум окнам.

**Делаем:**
1. **Меню-бар = простое нативное меню** (`NSMenu`): Старт/Стоп · Статус (строкой) · Открыть окно · Настройки ⌘, · Выход. Компактное, ничего не перекрывает. (Опционально: маленький индикатор уровня/таймер в самой иконке.)
2. **Одно окно** с боковой навигацией (`NavigationSplitView`): разделы **Live · История · Дашборд · Модели · Настройки**. Убираем отдельные окна Settings/Main и тяжёлый popover.
3. **Оформление** — системный «стеклянный» стиль: `NSVisualEffectView`/`.ultraThinMaterial` (Liquid Glass на macOS 26), матовые поверхности контента для читаемости. Сквозная семантика mic=teal / remote=amber.
4. Перенести существующие вьюхи (LiveView/HistoryView/DashboardView/SettingsView/ModelManager) под новую навигацию; выкинуть WindowManager-мультиокно.

**Стандарты:** snapshot/ui-логику не тестируем хрупко; тестируем презентационную логику (форматтеры, редьюсеры состояния) юнит-тестами. Обновить скриншоты/описание в README.
**Риск:** низкий (чистая Swift/SwiftUI работа, ядро не трогаем).

## Приоритет 3 — Android: реальный ASR (ORT-Android)

**Цель:** убрать mock — Android должен реально распознавать Parakeet.

**Делаем:**
1. **Получить ONNX Runtime под Android arm64**: либо официальные AAR/`.so` от Microsoft (`onnxruntime-android`), либо собрать. Положить `libonnxruntime.so` так, чтобы `sherpa-rs`/`sherpa-onnx` под Android слинковался.
2. **Собрать `.so` ядра с `--features ffi,sherpa`** под `aarch64-linux-android` (сейчас Android-сборка `ffi` = mock). Это главная сложность: `sherpa-rs-sys` должен найти ORT+sherpa под Android (возможно, придётся явно указать пути к предсобранным Android-либам или собрать sherpa-onnx под Android NDK).
3. **Поставка модели на телефон**: скачивание Parakeet (~640 МБ) через model_manager в `filesDir/models` (UI прогресса в Compose).
4. Проверка на реальном устройстве arm64 (RRT/качество).

**Стандарты:** инструментальный тест на устройстве (отдельно, не в обычном CI). Зафиксировать в README источник ORT-Android и лицензию.
**Риск:** высокий/средний — кросс-сборка ORT+sherpa под Android NDK исторически капризна; возможно несколько итераций. Память: parakeet int8 ~1.2 ГБ RAM — для слабых телефонов предусмотреть whisper-small или отказ.

## Приоритет 5 — Android: системный звук (с оговоркой)

**Реализуемо** через `MediaProjection` + `AudioPlaybackCaptureConfiguration` (API 29+), канал "remote".
**Оговорка (важно):** захватывается только звук медиа-приложений, не запретивших захват; **звонки и DRM-контент Android блокирует** системно. То есть это «звук с экрана/медиа», не «собеседник в звонке».
**Делаем:** запрос MediaProjection (системный диалог), второй `AudioRecord` с capture-config, foreground `type=mediaProjection`, push в канал "remote". Заглушка `SystemAudioCapture` уже размечена под это.
**Риск:** средний; UX-объяснение пользователю зачем «запись экрана».
